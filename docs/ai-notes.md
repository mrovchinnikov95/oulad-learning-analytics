# Где ИИ ошибся и что исправлено

Проект сделан с Claude Code. Здесь собраны ошибки агента из журнала этой работы: что было не так, кто или что это заметил и что изменили. Правила, которые закрывают эти ошибки, записаны в [CLAUDE.md](../CLAUDE.md).

Кто замечал:
- **гейт** — проверки сборки (`sql/25_raw_checks.sql`, `sql/90_checks.sql`) на реальном прогоне;
- **самопроверка** — агент перечитал свой код или разрезал результат до того, как писать вывод;
- **скриншот** — снимок отрисованного дашборда и `scripts/screenshot.mjs`, который падает на предупреждениях консоли;
- **ошибка инструмента** — psql, shell, таймаут;
- **рецензент** — один из четырёх независимых агентов, которые до публикации пытались сломать выводы, воспроизводимость с чистого клона, тексты и дашборд, у каждого свой контекст.

Главный вывод: в арифметике SQL ошибок не нашлось: независимый пересчёт и все рецензенты получили те же числа. Ошибки сидели в трёх местах: в допущениях о данных («вес — целое», «ноль — значит ноль», «срок у всех заданий значит одно и то же»), в проверках, которые могли пройти впустую, и в словах вокруг верных чисел («больше чем вдвое» при 1,97, «отписку не оформляют» там, где это следствие кодировки). Последние автор не видел совсем, их нашли только рецензенты.

## Данные и метрики

| Что ИИ сделал не так | Кто заметил | Что исправлено |
|---|---|---|
| Проверял вес задания как целое число. В наборе 14 дробных весов (12.5, 17.5, 7.5) | Гейт сырья на первом прогоне | Вес проверяется как десятичное число. Правило: формат поля проверять по всему файлу, а не по первым строкам |
| Посчитал долю «в срок» по TMA и CMA вместе. Разрез по модулям показал, что у CMA в BBB, CCC и DDD в срок почти никто не сдаёт, а в FFF и GGG — 94% | Самопроверка: разрез по модулям перед выводами | Правило `rules.on_time_measurable`: «в срок» только по TMA, CMA — в таблице качества данных (`cma_deadline`) |
| Объяснил это словами «срок у CMA означает что-то другое», не разобрав, что именно. В BBB, CCC и DDD сдачи приходят ровно через 2–3 дня после срока, а в FFF и GGG у всех CMA потока один общий срок в конце курса, так что 94% там значат «до конца курса» | Рецензент | Описано, как поле ведёт себя в каждом модуле; в AAA и EEE заданий CMA нет |
| По округлённому выводу 0,0% написал правило «ни одной сдачи CMA в срок». Счётчик дал 9 606 сдач вместо ожидаемых 30 526: в BBB и DDD нашлось по одной сдаче в срок | Самопроверка: сверка счётчика с ожидаемой суммой | Порог «меньше 1%», в тексте «2 из 30 526» |
| Разницу февраль — октябрь прикинул по округлённой таблице: 56,4 − 48,8 = 7,6 п.п. По неокруглённым долям — 7,5 | Самопроверка: сверка с `mart.readme_facts` | Числа выводов берутся только из `mart.readme_facts` |
| Написал «разрыв в активности к 12-й неделе становится больше чем вдвое». Отношение 76,9% к 39,1% — 1,97; разрыв в пунктах вырос в 2,4 раза только от недели 0, а «первая неделя» по-русски — неделя 1 | Рецензенты, трое из четырёх | «Почти вдвое», «на неделе 12»; недели называются как в данных |
| Рядом с девятью парами «февраль — октябрь» поставил общие доли 48,6% и 54,4%, хотя в октябрьскую входят ещё четыре потока без пары (оба потока AAA с самой высокой долей сдавших) | Рецензент | Сравнение только по парам |
| Не сказал, что вывод про февраль держится на знаке: по отдельности значимы четыре пары из девяти, а от всех регистраций в паре FFF 2013 февраль выше | Рецензент | Оговорка в выводе |
| «Отписку они не оформляют» подал как наблюдение о поведении. В наборе отписавшимся ставится итог Withdrawn, поэтому у провалившихся отписки нет по определению | Рецензент | Вывод переписан от кодировки итога |
| Рекомендовал «неделя без входа — повод написать». Такая неделя есть у двух третей тех, кто курс сдаёт: правило почти не отличает рискованных | Рецензент | Рекомендация — смотреть на несколько недель подряд |
| Про первое задание написал «задолго до отписки» и не назвал охват: обычно отписка через четыре недели, но не всегда; первое задание пропускает примерно каждый пятый из будущих несдавших. И объяснил связь тем, что задание входит в оценку, хотя в четырёх потоках его вес 0, а разрыв там такой же | Рецензент | Срок, охват и вес названы в выводе, рекомендация — с оговоркой, что эффект звонка данные не измеряют |
| Написал, что 3365 регистраций без кликов «остаются в знаменателях», хотя большинство из них отписались до старта и в поток не входят | Рецензенты | Текст в README и в `qa.data_quality` |
| В английском абзаце назвал регистрации «students» без оговорки | Рецензенты | Определение «студента» в обоих абзацах, на дашборде — подпись плитки |
| Писал в выводах «студентов», хотя считаются регистрации на поток: один человек бывает в нескольких потоках | Самопроверка текста | Определение в README и правило в CLAUDE.md |

## Проверки

| Что ИИ сделал не так | Кто заметил | Что исправлено |
|---|---|---|
| Сверку итогов приступивших упаковал в одно число: четыре счётчика с множителями 10⁶, 10⁴ и 10². При 12 361 приступивших с итогом Pass разряды перекрываются, и разные наборы чисел дают одно значение | Самопроверка до запуска | Сверка по каждому итогу, с проверкой, что сопоставлены все четыре |
| Сверка «должны сдать» по заданиям прошла бы на пустом соединении: 0 расхождений из 0 строк | Самопроверка | Число соединённых заданий входит в результат проверки |
| Порчу CSV в тесте писал через sed с якорем конца строки. Файлы OULAD — с CRLF, шаблон бы не сработал, и тест «прошёл» бы, ничего не испортив | Самопроверка (`od -c`) до запуска | Шаблоны без якоря конца строки |
| Случай «потерянный факт» в тесте порчи писал как представление (VIEW), которое читает само себя: это ошибка создания, а не проверка | Самопроверка | Старое представление переименовывается, новое читает его |
| В четырёх подменах правил в `scripts/test_controls.sh` функция объявлялась с другими именами параметров; `CREATE OR REPLACE` падал раньше проверки, тест поймал 25 порч из 29 | Сам тест: он отличает падение «не той» проверкой от пойманной порчи | Те же имена параметров, правило — в шапке теста |
| `scripts/test_pg_version.sh` звал psql без переменных PG*; запрос падал внутри `$(…)`, а тест печатал «ok» с пустой версией | Самопроверка вывода теста | Подключён `env.sh`, версия берётся отдельной командой, падение останавливает тест |
| Отпечаток объектов в `scripts/test_idempotency.sh` склеивал `relkind` без приведения и группировал по выражению с `count(*)`. Исправление лежало в рабочем дереве, а в журнале уже стояло «исправлено» | Ошибка psql; рецензенты заметили, что в коммите исправления нет | `relkind::text`, группировка по колонкам, коммит и повторный прогон |
| Тест порчи запускал сборку на испорченных данных с логами в общий `.tmp/`, и `make check` после `make test` сверял README с логом упавшей сборки. `make check` зависел от `.tmp/test_controls.out`, который никто не писал | Рецензенты: воспроизводимость с чистого клона | `LOG_DIR` у тестов, `make test` пишет свой лог, порядок `test` → `check` |
| Проверку «график не шире карточки» сначала написал по контейнеру графика; vega-embed растягивает сам контейнер, и проверка не поймала заведомо широкий SVG | Контрольный прогон на испорченной странице | Меряется карточка; проверка сразу нашла обрезку графика итогов на телефоне |

| В двух проверках витрин приведение типа стояло прямо в `WHERE` и соединение не проверяло число строк, вопреки собственным правилам | Рецензент | `CASE` с `rules.na`, число сопоставленных строк входит в проверку |

## Что из этого следует для работы с ИИ

- Перед выводом разрезать метрику по главным измерениям: среднее прячет поломку в части данных.
- Не верить округлённому выводу, когда текст говорит «ни одного» или «все».
- Каждую проверку сначала заставить упасть на заведомо плохих данных (`scripts/test_controls.sh`) и проверить, что она не проходит на пустом множестве.
- Итоговые числа подтверждать вторым расчётом, который писался без доступа к первому.
- График принимать по картинке, а не по коду спеки.
