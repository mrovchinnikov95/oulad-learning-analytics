# CLAUDE.md

Правила для Claude Code в этом репозитории. Файл начался с постановки задачи и дополнялся по ходу работы, когда находились ошибки: главные описаны в [docs/ai-notes.md](docs/ai-notes.md), а правило, которое их закрывает, записано ниже.

## Задача

Витрины на открытом наборе OULAD (Open University, 2013–2014): сдача заданий, сдача в срок, успешность по модулю и потоку, активность когорт по неделям. Слои `raw → clean → mart` в PostgreSQL, проверки, которые останавливают сборку, независимый пересчёт на Python, статический дашборд на GitHub Pages, README с выводом сверху. Источник истины по определениям — [docs/spec.md](docs/spec.md), а не память модели и не README.

## Стек и окружение

- PostgreSQL 16+. `HEADER MATCH` в `\copy` есть с 15-й версии. Не использовать того, что появилось только в 17-й. Сборка прогоняется на 16 и 17, выгрузки обязаны совпасть побайтно (`scripts/test_pg_version.sh`).
- Локальный кластер — только через `scripts/pg_local.sh` (`./.pgdata`, порт 54331). На macOS postmaster стартует только с `LC_ALL=C`.
- Подключение — переменные `PG*` из `scripts/env.sh`; `psql` всегда с `-X -v ON_ERROR_STOP=1`.
- Python 3 с pandas. Любой Python, который читает скачанные данные, запускать с `python3 -I`.
- Данные OULAD в репозиторий не коммитятся: `scripts/get_data.sh` качает их и сверяет с `data/SHA256SUMS`. В репозитории — только агрегаты в `dashboard/data/`.
- CSV OULAD — с окончаниями строк CRLF. Правки файлов в тестах не должны опираться на конец строки (`$` в sed).

## Слои

- `raw` — файлы как есть: все поля текстом и номер строки файла. Никаких преобразований.
- `rules` — все правила в функциях (`sql/05_rules.sql`): неделя курса, «отписался до старта», «числится на курсе в окне дней», «в срок», группа итога, какие задания входят и у каких мерить срок. Витрины, факты и проверки вызывают их; в `sql/90_checks.sql` ожидаемые значения граничных случаев записаны ещё раз отдельно, чтобы сверить с ними функции.
- `clean` — типы, `?` → `NULL`, ключи. Строится только после проверок сырья.
- `mart` — витрины с аддитивными числами (численник и знаменатель рядом), доли — из них.
- `qa.data_quality` — только предупреждения; ошибки останавливают сборку раньше.

## Правила SQL

- Проверки сырья читают `raw` напрямую. Приведение типа — внутри `CASE` после проверки формата: PostgreSQL не гарантирует порядок условий в `WHERE`.
- Не угадывать формат по первым строкам: вес задания бывает дробным (`12.5`). Формат каждого поля сначала проверить по всему файлу.
- Пересборка `clean` и `mart` — `DROP ... CASCADE` и `CREATE TABLE AS` в одной транзакции; загрузка `raw` — `TRUNCATE` и `\copy` в одной транзакции.
- `\copy` не подставляет переменные psql в свою строку: каталог данных задаётся через `\cd :data_dir`.
- Источник для `CROSS JOIN` — агрегат без `GROUP BY` (ровно одна строка). Пустой CTE в соединении молча обнуляет результат.
- Проверка на соединении обязана проверять и число соединённых строк: пустое соединение даёт «0 расхождений».
- Сортировка выгрузок по тексту — `COLLATE "C"`.
- Не опираться на текст сообщений сервера: он переводится по `lc_messages`. В тестах — своя метка в выводе (`fp|`) или код SQLSTATE.

## Расчёты для выводов

- Число в выводе считается из неокруглённых значений в `mart.readme_facts`, а не из округлённой таблицы: разница 56,4 − 48,8 даёт 7,6 п.п., а неокруглённая — 7,5.
- «Ноль» в выводе запроса с округлением — не ноль: перед словами «ни одной» смотреть точный счётчик.
- Метрику проверять в разрезе до вывода: средняя доля «в срок» по всем заданиям прятала 0% у CMA в трёх модулях.
- Связь — не причина: у несдачи первого задания и провала может быть общая причина. Вес задания разрыв не объясняет (в четырёх потоках он 0, а разрыв тот же) — такие объяснения тоже проверять данными.
- Знаменатель называть явно: «из приступивших», «из тех, кто должен был сдать». Общую долю не ставить рядом со сравнением пар, если в неё входят потоки без пары.
- Кратность считать, а не прикидывать: 76,9% против 39,1% — «почти вдвое» (1,97), а не «больше чем вдвое». Номер недели писать как в данных: «неделя 12», недели считаются с нуля.
- Наблюдение не должно быть следствием кодировки: у итога Fail нет отписки по определению набора, это не поведение студентов.
- У правила-сигнала называть и точность, и охват, а у рекомендации — что данные её не проверяли.
- Объяснение странности в данных проверять так же, как число: «срок CMA значит другое» сначала разобрать по модулям.
- «Студент» в тексте — регистрация на поток: один человек бывает в нескольких потоках.

## Проверки — обязательны после любой правки

```bash
make build test check screenshot
```

- `sql/25_raw_checks.sql` и `sql/90_checks.sql` запускаются внутри `scripts/build.sh`, падают громко и печатают все проверки; при падении выгрузка не перезаписывается. Тесты пишут логи в свои каталоги (`LOG_DIR`), чтобы не затирать логи рабочей сборки.
- Исправление в рабочем дереве — ещё не исправление: перед словом «исправлено» в журнале — коммит и повторный прогон теста.
- `checks/verify_independent.py` написан по `docs/spec.md` без доступа к SQL. Правка SQL, после которой он расходится, — ошибка, пока не доказано обратное. Его не подгонять под SQL. Меняется определение — сначала `docs/spec.md`, потом оба расчёта.
- Новый контроль сначала заставить упасть на заведомо плохом входе (`scripts/test_controls.sh`) и пройти на заведомо хорошем.
- Числа в README — из `mart.readme_facts`, `qa.data_quality` и логов проверок; `checks/check_readme_numbers.py` проверяет, что каждое число в проверяемых блоках есть среди них (плюс недели 0 и 12, годы набора и число из `OULAD.names`), но не то, что оно стоит на своём месте. Таблицу по модулям рендерит `--write`.
- Дашборд принимать по скриншоту, а не по коду спеки: `scripts/screenshot.mjs` падает на любом предупреждении Vega-Lite в консоли и на графике шире своей карточки (мерить карточку: vega-embed растягивает контейнер графика). Один цвет — одна сущность на всей странице; ось — величина, которая одинаково значит для всех линий (день срока, а не номер задания).
